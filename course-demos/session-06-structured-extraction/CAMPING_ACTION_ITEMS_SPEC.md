# L5 演示设计：露营群聊里，到底谁负责帐篷？

状态：已实现并验收。本文保留设计契约；具体命令及实测记录见 [课堂运行说明](CAMPING_DEMO.md)。全课程测试 248 项通过。

对应：Session 06 `extract_tasks.py`、Session 07 `task_system.py`。

## 1. 为什么换成这个例子

几个朋友准备周六露营，在群里讨论装备、拼车和食物。有人重复承诺，有人把截止日期提前，有任务尚未认领，还有玩笑和未确定的想法。

开场展示聊天，讲师问：

> 如果现在直接把群聊变成提醒，会不会催错人、建出重复任务，或者把“我负责吃”也当成工作？

学生不需要理解支付故障、数据库连接池或 Jira。熟悉场景让注意力集中在 L5 的核心问题：怎样把自然语言变成可处理的数据，以及如何检查、修正和使用这些数据。

这是虚构聊天记录，用类似聊天窗口的文本展示即可，不接微信或真实群，不发送通知、不预订、不采购。

## 2. 教学主线与两份代码的分工

```text
固定群聊
   ↓ Session 06
识别已确定的行动 → 输出结构化记录 → 解析/校验 → 有限重试
   ↓ 原始行动记录（保留跨消息重复及来源）
   ↓ Session 07
去重并合并来源/截止日 → 排序 → 区分未分配任务 → 模拟提醒
```

| 教学问题 | 用哪段情节说明 | 所属环节 |
|---|---|---|
| 什么是行动，什么只是聊天？ | “我负责吃”和“也许买无人机” | 提取规则与事实核验 |
| JSON 为什么不能直接信？ | 未知负责人、非法日期、内部尾逗号 | 解析/校验 |
| 重试能做什么？ | 错误记录被指出后重新输出 | 有限重试 |
| 合法值为什么仍可能错？ | 把阿杰的任务误写给小雨 | 回到原文，不靠 schema 判断 |
| 同一件事说两次怎么办？ | 重复确认领帐篷，截止时间提前 | 去重、字段合并 |
| 相似文字是不是同一任务？ | 领取帐篷与归还帐篷 | 误合并边界 |
| 没人认领的任务怎么办？ | 准备音箱 | null 与待分配队列 |
| 什么时候催谁？ | 截止日和未完成状态 | 模拟时钟与提醒 |

不加入新的评估模型或复杂 Agent 框架。承接 L4 的结论：结构合法不等于事实正确。课堂只看讲师演示和讨论，所有编码与实验放在课后。

## 4. 提取任务与人工参考结果

### 给提取器的任务要求

> 从聊天中提取已明确确认的筹备行动。每条消息独立保留明确的任务承诺及来源，跨消息重复交给后处理。不得把玩笑、未确定提议、泛泛回应或对已有事项的无新信息附和新增为任务。负责人未落实时写 null，截止日未知时写 null。明确“高优先级”记 high，“低优先级”记 low，普通或未指定记 medium。不要根据个人常识提高优先级。不要编造负责人或日期。

这里有意采用“逐消息行动记录”，所以 m02、m06 都保留，截止日分别为 18 日和 17 日；不要求 LLM 先完成跨消息去重。m06 的原文证据要保留，便于解释日期合并。

### 原始记录与最终清单

人工参考：提取 **8 条原始记录**，合并 m02/m06 后得到 **7 项任务**。

| 最终任务 | owner | due | priority | 来源 |
|---|---|---|---|---|
| 领取租用的帐篷 | jie | 2026-09-17 | high | m02、m06 |
| 确认拼车名单 | ning | 2026-09-17 | high | m04 |
| 购买食材 | yu | 2026-09-18 | medium | m03 |
| 检查炉具 | peng | 2026-09-18 | medium | m05 |
| 归还租用的帐篷 | jie | 2026-09-21 | medium | m07 |
| 准备音箱 | null | null | medium | m08 |
| 整理露营歌单 | peng | 2026-09-18 | low | m09 |

表格是教学参考顺序：先优先级，再截止日；没有日期排在同优先级末尾。同优先级、同日期保持输入顺序。

真实模型可能多提、漏提或措辞不同，应展示实际偏差。不能通过后台静默替换成参考结果来宣称提取成功。

## 5. Session 06：让失败可见

### 5.1 输出契约

保留原来的四个业务字段，新增一条来源依据：

```json
{
  "task": "领取租用的帐篷",
  "owner": "jie",
  "due": "2026-09-18",
  "priority": "high",
  "evidence": {
    "message_id": "m02",
    "quote": "我负责领取租用的帐篷，9 月 18 日前完成。这件设为高优先级。"
  }
}
```

输入中显式传入成员映射、固定当前时间和聊天消息，不依赖机器当天日期。按以下顺序校验：

1. 顶层为数组，每项为对象；task/owner/due/priority/evidence 必须存在。
2. task 为去除空白后非空字符串；owner 为已知 ID 或 null。
3. due 为 null 或严格 YYYY-MM-DD 字符串，且是真实日历日期；不把数字强转成日期。
4. priority 为字符串且在枚举内，类型错误返回可读错误，不抛出未处理的 TypeError。
5. evidence 的消息 ID 存在，quote 为该消息非空连续子串。

不强制任务数为 8，不禁止空数组用于其他输入；不能将参考答案硬编码为通用业务校验。

引文校验只证明引用存在，不证明负责人、日期或任务一定被正确理解。事实错例仍需要人对照原文。

### 5.2 五个讲师可切换的演示场景

| 场景 | 输入/模型响应的变化 | 预期画面 |
|---|---|---|
| normal | 正常的人工参考响应或真实模型结果 | 输出原始任务及来源 |
| prose | 合法 JSON 前后有说明文字 | 容错提取成功，不触发修正 |
| repair | 第一次出现内部尾逗号；第二次是合法 JSON 但 owner 未知、日期不合法；第三次纠正 | 解析失败 → 字段失败 → 成功，恰好三次调用 |
| exhausted | 每次都返回不合法字段 | 最多三次后明确失败，不产生可交给下游的成功文件 |
| semantic-error | JSON 和所有字段合法，引用 m02，但 owner 写成 yu | 校验通过；对照原文发现事实错误 |

repair/exhausted 是预先编排的人工响应回放，必须明示。它们证明控制流程，不证明模型理解反馈。prose、semantic-error 也属于人工构造的边界案例，不混称为真实模型实验。

主流程允许一次初始调用加两次重试。下一轮包含原始对话、上一轮原始输出、错误清单及修正要求；将待评文本明确标成数据。

本业务循环只针对解析/校验失败。API 异常另行记录并退出；底层网络重试按公共客户端配置执行，不将网络故障记成“任务质量差”。耗尽后输出失败报告，不假装已经告警或通知了人工。

## 6. Session 07：从八条记录变成七项任务

### 6.1 先展示重复，再展示误合并风险

第一个画面：m02 与 m06 都是领取帐篷，负责人一致，展示合并前后的来源和截止日。

合并规则：保留第一条可读描述；来源去重后全部保留；截止日取更早的已知值；优先级取更高等级。把采用了哪条规则打印出来。

**业务边界**：本演示采用保守的更早截止日策略，不宣称它能正确处理“延期”或全部任务更新。第一版不处理取消、转交、延期和版本冲突；遇到这些类型需人工确认，不能静默套用合并规则。

第二个画面：同一负责人的“领取租用的帐篷”和“归还租用的帐篷”文字相似，却是两件事。不能只凭主题词“帐篷”合并。

### 6.2 中文相似度：明确采用教学基线

现有 tokens() 只匹配英文字母和数字，直接喂中文会得到空词集合。本场景不能原样复用该 tokenizer。

第一版采用可选择的中文字符二元组 Jaccard：统一大小写，在连续字母/数字/汉字序列内取相邻两个字符组成集合；空白和标点作为边界，不跨边界拼接，不调用 LLM 计算相似度。旧英文词集合方式保持默认兼容。

这是一种可解释的词面基线，不具备语义理解。主回放尽量使用短、统一的任务描述，避免把分词研究变成本节新主线。

以“领取租用的帐篷”与“归还租用的帐篷”为例，两者相似度为 4/8 = 0.5；两条完全相同的领取描述为 1.0，已用单元测试核验。主讲默认阈值 0.6 保留领取/归还两项、合并重复领取；降到 0.5 演示误合并。

只有 owner 已知且相同才自动合并。两个 owner=null 不代表同一人，不自动合并；放入待分配清单并保留来源。

更换成真实模型输出的不同措辞后，结果可能变化。不要暗中标准化成参考答案；展示实际相似度，说明阈值依赖数据。

### 6.3 排序、待分配与提醒

主界面分两个简短区域：

- 已分配任务：按优先级、截止日排序。
- 待分配任务：单独展示“准备音箱：负责人待定，截止日待定”，不输出 `@None`。

模拟时钟从 2026-09-17 到 2026-09-21（包含端点）：

- 9 月 17 日：提醒阿杰领帐篷、宁宁确认拼车。
- 9 月 18 日：提醒小雨购买食材、大鹏检查炉具和整理歌单。
- 9 月 21 日（周一）：提醒阿杰归还帐篷；对已逾期、未完成且有负责人的任务展示周一催办。

默认没有完成记录，因此周一催办此前 5 项到期任务；真实世界可能已经做完，系统不知道。人工完成快照标记领取帐篷和确认拼车已完成，同一周一逾期提醒降至 3 项。快照的 as_of 为 9 月 21 日；不能倒用于更早日期。

当天到期和逾期扫描都排除 done=true。未定负责人不发送个人提醒；没有截止日不自动推断日期。只打印模拟提醒，不真的发消息。

## 8. 课后作业

### A：故障诊断（必做）

使用同一群聊，运行三类故障：解析错误、非法字段、合法但事实错误。记录在何处被发现、调用次数及最终状态；区分回放与真实模型。提交失败后成功及重试耗尽的日志。

### B：任务管理规则（必做）

用带人工标签的任务对扫描阈值，记录逐对判断及误合并/漏合并。固定 fixture 已包含领取/归还近似负例和词面差异大的同义正例；预检同时出现误合并和漏合并。不能只用原始七项清单统计剩余数。

提交一份加入完成状态前后的提醒对照，解释为什么没有负责人或日期的音箱任务不能直接提醒个人。

### C：扩展（选做）

只选一个：相对日期解析、延期需要人工确认、任务转交、语义去重。明确输入契约和失败行为，不声称修改一个阈值就能处理所有变化。

## 9. 实现文件与边界

本节保留事故案例和默认命令，新增露营 fixture 与明确参数。共享校验位于 `course-demos/common/task_contracts.py`；完整命令见运行说明。

```text
session-06-structured-extraction/
  CAMPING_ACTION_ITEMS_SPEC.md         # 本设计
  fixtures/camping_chat.json           # 原文、时间、成员表
  fixtures/camping_responses.json      # 有指纹绑定的人工回放
  prompts/camping_extraction.md        # 提取约束与证据要求
session-07-action-items/
  fixtures/camping_pairs.json          # 标注任务对
  fixtures/camping_done.json           # 人工完成状态与对应任务身份
course-demos/outputs/camping/<run-id>/
  extraction_report.json
  extracted_tasks.json                 # 只在成功时生成
  task-runs/<run-id>/task_report.json   # 每次下游运行独立保存
```

改造原则：

- 复用 Session 06 的解析、校验和有限重试思路，用场景配置传入成员等信息，不覆盖事故团队名单。
- 提取校验补齐日期、必填字段和类型边界；证据字段为露营契约要求，旧事故入口仍接受四字段记录。露营模型输出拒绝 done 等额外状态字段。
- Session 07 支持可选相似度策略、合并日志、待分配清单、完成状态和统一 done 过滤；事故入口继续使用旧英文策略。
- 任务身份由程序在去重后生成；完成状态必须引用该次提取输入指纹及稳定任务 ID，不能按列表行号标记。第一版不跨不同提取结果自动继承完成状态。
- 主流程必须明确读入本次成功文件；新 run-id 隔离失败结果，不能在失败后自动读取上次留下的 JSON。
- 回放绑定完整群聊、成员/日期上下文和提示词版本。修改输入后不得借用旧人工输出；无 Key 时明确回放，真实失败不静默回放。
- 每次报告记录模式、输入、原始响应、校验错误、调用次数、成功/失败状态及实际合并理由；不记录密钥。


## 10. 验收标准

### 教学验收

- 正常人工回放输出 8 条记录、合并为 7 项任务；没有吃饭玩笑或无人机购买任务。
- 两条领取承诺合并后保留 m02/m06 两个来源及更早日期；领取和归还在主阈值下保持分离。
- 降低阈值能复现一次误合并；不把人工选例结果当生产调优结论。
- 原文、结构化记录、最终任务及提醒之间可以逐条追溯。
- 显示合法但负责人错误的反例，不能将引文存在当作事实校验通过。

### 程序验收

- prose 被正确容错，尾逗号解析失败，非法日期和未知 owner 返回可读错误。
- 缺失字段与 null 区分；priority 类型错误不使校验器崩溃。
- repair 三次后成功；exhausted 三次后失败且不产生成功任务文件；下一轮包含前次响应与错误。
- 证据 ID/连续引文有效性检查通过；引文语义支持保留人工审阅边界。
